# Mono Slide PDF（モノクロ＋差し色 スライド風PDF化）

## 由来

Googleチャット・カレンダー社内活用ガイド（260729_第1回会議資料）を、画面投影用の
横長16:9スライド風PDFに変換したセッションで確立したデザイン・実装パターン。
ユーザーから「めちゃくちゃ良かった」と高評価だったため、毎回ゼロから組み立て直さず
このSkillを起点にすること。

配色は [`color-mono`](../color-mono/SKILL.md) をそのまま使う。color-monoは配色ルールのみを
定義するSkillで、こちらはその配色を使って「元ドキュメントをスライド風PDFに変換する」
一連の作業フロー（構成・図解化・実装・PDF化・検証）を定義する。

### ★ ゴールドスタンダード参考例

`reference-best-example.html` は、このSkillの中でユーザーから「一番よかった」と
名指しで評価された実例（密度・赤字の強調具合・黒字の太さ/サイズのバランス）。
新しいスライドの「詰まり具合」や「強調の強さ」に迷ったら、まずこれを開いて見比べる。
ファイル内のHTMLコメントに、何が効いているかの判断基準を5点まとめてある。

## 起動条件

- 「スライドっぽいPDFにして」「16:9のPDFで」「スライド形式のPDFにして」
  「資料をスライドPDF化して」「/color-mono でPDFにして」
- Googleドキュメント/Word/テキストなど文章主体のドキュメントを、画面投影・配布・
  一枚読み物用のPDFに変換したいとき
- 縦長（配布・印刷・スマホ閲覧向け）を明示されたときも同じ配色・フォントで対応する

技術者向けの詳細仕様書や、DADS/ブランドカラー指定がある案件には使わない
（その場合は `color-dads` / `color-brand` を使う `dads-html` 等に譲る）。

## 全体フロー

1. **元ドキュメントを全文取得する**（Google Docs MCP の `read_file_content` 等）。
   要約・圧縮はしない。ユーザーが「かなり練って作った」ドキュメントであることが多く、
   再要約は望まれない。誤字脱字だけ適宜修正してよい。
2. **向きを決める**。ユーザー指定があればそれに従う。無ければ用途から判断する：
   - 画面投影・会議で映す → **横長 landscape**（`template-landscape.html`, 1280×720 / 16:9）。
     「スライド」らしく、1トピック1ページ・余白にもゆとりを持たせる。
   - 配布資料・印刷・スマホでの一枚読み物 → **縦長 portrait**（720×1280 / 9:16）。
     縦長にはさらに2つのパターンがあるので、資料の性格で選ぶ（詳細は下記
     「4. 縦長(portrait)の2パターン」）：
     - **スライド分割型**（`template-portrait.html`）：見出し単位で1ページ1トピックに
       区切る。ページ数が資料の構成そのものを表す資料（章立てを明示したい提案書等）向け。
     - **ドキュメント流し込み型**（`template-portrait-doc.html`）：docx/Wordのように
       本文を上から連続して流し込み、ページはみ出した分だけ自然に変わる。「ページで
       区切らないでほしい」「下の余白が気持ち悪い」と言われたらこちら。カタログ・
       レポート・ガイドなど文書然とした資料のデフォルトはこちらを優先してよい。
       さらに、**1〜2ページ程度で収まりそうな資料なら、複数ページに分けず
       コンテンツ高さぴったりの単一ページにする**（詳細は下記「4. パターンB'」）。
       最終ページの余白が気になる／気にされそうな場合はこちらを優先する。
3. **該当するテンプレート（`template-landscape.html` / `template-portrait.html` /
   `template-portrait-doc.html`）を作業用にコピー**して、スクラッチパッドで編集する
   （元テンプレートは直接壊さない）。
4. **見出し単位で1スライド1トピックに分割**する。テンプレート内のコンポーネント
   （下記「コンポーネント一覧」）をコピペしながら、元ドキュメントの構造に当てはめる。
   - 箇条書きが並ぶだけの内容 → `card` グリッド（`grid2`/`grid3`/`grid4`）
   - 時系列の経緯 → `timeline`（横長）/ `timeline-v`（縦長）
   - 現状→対応の対比 → `ba-wrap`（横長）/ `ba-stack`（縦長）
   - プロセス・フロー → `flow`（横長）/ `flow-v`（縦長）
   - 「これだけは伝えたい」という核心メッセージ → `callout-strong`
   - Before/Afterのマッピング（A→Bの変換規則など） → `mapping-row`
   - 補足・宿題・参考資料など優先度の低いページは**デッキの一番最後**に回す
5. **文字は大きめ・余白は自然に埋める**（詳細は下記「レイアウトの原則」）。
6. **Chromeヘッドレスで PDF 化**し、`pypdfium2` でページを画像化して**必ず目視確認**する
   （はみ出し・余白の偏り・文字切れがないか）。問題があれば HTML を直し、再変換して
   再確認するループを、完成するまで回す。
7. 完成したPDFを `SendUserFile` でユーザーに渡す。

## レイアウトの原則（このSkill最大の学び）

### 1. 文字は大きめに、余白は「自然に」埋める

第一稿でありがちな失敗は、フォントが小さく余白が不自然に余ること。以下のルールで防ぐ：

- 本文は 16〜18px 以上、見出しは 19〜24px 以上を基本にする。
- `.slide` は `display:flex; flex-direction:column` にして、ヘッダー（eyebrow/title/
  subtitle/rule）を固定サイズ、`.content` を `flex:1` にして残り高さを埋めさせる。
- **内容が薄いスライド**（カード内が2〜3行で終わるなど）は、カードを引き伸ばして
  無理に埋めるのではなく、`.content.center` でブロックごと縦中央に寄せる。
  上下に均等な余白ができ、「はみ出しはないが空虚でもない」状態になる。
- **内容が濃いスライド**（4象限カードなど、各カードにそれなりの文章がある）は、
  `grid4`/`grid3` をそのまま `flex:1` の `.content` に入れて高さいっぱいに引き伸ばす。
  カード内は `justify-content:flex-start`（上詰め）がデフォルト。文章量が少ない
  1枚だけ短い場合に不自然な中央寄せにならないようにするため。
- 3ブロック以上を1枚に収めたい場合（将来構想の②段構成など）は `.content.stack`
  （`space-evenly`）を使うと、ブロック間の余白が均等に配分される。

### 2. はみ出しは必ず目視で潰す

- フォントサイズや行間を上げるとすぐ `grid4`（2×2で高さ固定）のカードから
  文章がはみ出す。padding を詰める（`22px 28px` 程度）、`line-height` をやや
  詰める（1.55〜1.65）、ヘッダーの余白（`.rule` の margin-bottom 等）を削る、
  の順で対処する。
- 1回のPDF化で終わらせず、`pypdfium2` で全ページ（最低でも文字量の多いページ）を
  画像化して `Read` ツールで見る。特に `grid4` ページ・`content.stack` を使った
  詰め込みページは要チェック。

### 3. 差し色は1資料1色、強調は「太めの2pxボーダー」で統一する

- 差し色（`--mono-accent`）を使ってよい場所は、**「ここだけは強調したい」ボックス
  （`.card-highlight` / `.flow-box.flow-highlight` / `.callout-strong`）と、eyebrow・
  タグなど資料全体で共通の小さな装飾要素**のみ。
- **カタログ・一覧の連番（`.cat-num`）や、単なる手順番号のバッジ（`.badge-num`）を
  既定で赤にしない。** 項目が多い一覧（10件以上並ぶAPIカタログ等）で番号や見出しを
  すべて差し色にすると、「本当に注意すべき箇所」が埋もれて資料全体が赤っぽく見える、
  というユーザーからのフィードバックがあった。`.badge-num` は既定で `--mono-ink`
  （黒系）にし、`.card-highlight` の中にあるときだけ赤くする
  （`.card-highlight .badge-num { background: var(--mono-accent); }`）。
  `.cat-num` も `--mono-faint`（薄いグレー）にする。
- **`.card-highlight` を使うのは「読み手が見逃すと困るリスク・警告・結論」だけ**に
  絞る。「公式機関の紹介」「まとめの一言」のような単なる情報カードには使わない。
  迷ったら「これが無いと読み手が損をする/誤解する情報か？」で判定する。
- 強調ボックスはいずれも「background: accent-tint + border: 2px solid accent」で
  統一されている。1pxの薄い枠と2pxの強調枠が混在すると、資料全体の強弱にブレが
  出るので避ける。
- 例外：GASの自動色分け例のように、**実際のプロダクト機能の色**（Googleカレンダーの
  ラベル色など）を説明する図解は、情報として正確な色を使ってよい（`color-dot` 参照）。
  これは装飾目的の差し色ではなく、事実を示すための色なので `color-mono` の
  「差し色1色」ルールの例外として扱う。

### 4. 縦長(portrait)の2パターン：スライド分割型／ドキュメント流し込み型

横長版で確立した「余白は自然に埋める」（`.content.center` でブロックごと中央寄せする）
方針を、縦長にそのまま持ち込まない。縦長にはさらに2つの実装パターンがあり、
資料の性格に応じて使い分ける。

#### パターンA：スライド分割型（`template-portrait.html`）

見出し単位で1ページ1トピックに区切る、`.slide { height:1280px; page-break-after:always; }`
方式。章立てを明示したい資料（提案書・議事録など、ページ数=構成の見せ方に意味がある
資料）向け。ユーザーからのフィードバック：

> 縦のときは、Slideっぽいというよりは、ちゃんと密にギチギチに詰めてほしい。

- `.content.center` で余白を上下に逃がすのではなく、**ページの上から自然に流し込む**
  （`.content.stack` や素の縦積みで、コンテンツ量なりに高さを使わせる）。
- 1ページに収める情報量は、横長の「1トピック1ページ」より多めでよい。関連する
  複数のカード・見出しを1ページにまとめて、ページ数を絞る方向に倒す。
- とはいえ「気持ちよく詰める」であって「窮屈に見える」のはNG。padding・行間は
  読める範囲で詰め、はみ出し確認（後述）は横長以上に丁寧に行う。

#### パターンB：ドキュメント流し込み型（`template-portrait-doc.html`）

`.slide` のような固定高さdivを使わず、本文を上から連続して流し込む方式。ページ区切りは
一切手動で入れず、はみ出した分だけChromeの印刷エンジンが自然に次ページへ送る＝docx/Word
と同じ挙動になる。ユーザーからのフィードバック：

> ページ変更しなくて良いんです。下にある余白が気持ちが悪いので。docxのときは
> そういう分け方しないでしょ。
>
> 縦のときは、文字が小さくなってもいいです。投影するようではないので。所謂Wordとか
> でやるようなドキュメントに近いUIを想定しています。どんどん上に詰めてください。

- カタログ・レポート・ガイドなど「文書として読む」資料は、**まずこちらをデフォルト
  候補にする**。「スライド風に」と明示されない限り、パターンAより自然に収まりやすい。
- 文字サイズはパターンAよりさらに小さくてよい（本文13px前後、見出し19〜26px程度）。
  投影用ではないため可読性さえ保てば詰めるほど良い。
- **`@page` の `margin` は必ず `0` にし、左右上下の余白は本文コンテナ（`.doc`）自身の
  `padding` で作る**（`@page { margin: 0 }` + `.doc { width:720px; padding: 40px 34px
  32px 34px; }`）。これは横長`template-landscape.html`／パターンA `template-portrait.html`
  が最初から採用している実装と揃えるためで、**`@page margin`を使う方式は避ける**。
  理由：`@page margin`はページの余白を削って「印字可能領域」を縮小する形で効くため、
  子要素の幅指定やテキストの折り返し幅の計算がブラウザ実装依存になりやすく、実際に
  このSkillの開発中も「左右の余白が気になる」という指摘を受けて`@page margin`方式から
  `padding`方式に直した経緯がある。最初から`padding`方式で組めば、この手戻りを避けられる。
- 改ページ制御はCSSのbreak系プロパティで行う。手動のページ区切りは入れない：
  - `.card` / `.callout-strong` / `.cat-row` に `break-inside: avoid`
    （カードや行の途中でページが割れるのを防ぐ）
  - `h2.sec-title` / `.cat-section-title` に `break-after: avoid`
    （見出しだけがページ末に取り残されるのを防ぐ）
- セクションの切り替わりは強制改ページではなく `.part-divider`（左に太いアクセント
  バーを立てる）のような**視覚的な節目**で表現する。
- ページフッター（ページ番号など）は基本つけない。`position:absolute` の `.footer` は
  固定高さの `.slide` 前提の実装なので、流し込み型には使えない。出典等を書きたい
  場合は文書の末尾に `.doc-footnote` を1回だけ置く。
- どちらのパターンでも、どのくらい詰めるかは資料の分量・用途次第（厳密なルール
  ではなく方針）。パターンAで迷ったら「1ページの下部に不自然な空白が残っていない
  か」、パターンBで迷ったら「見出しやカードの途中で不自然にページが割れていない
  か」を基準にする。

#### パターンB'：1枚に収める（コンテンツ高さぴったりの単一ページ）

パターンBでも、複数ページに分かれる場合は**最後のページの下に余白が残る**現象が
構造的に発生する（本文量がページの整数倍にちょうど収まる保証がないため）。これは
CSSでは消せない（Wordの文書でも最終ページが白紙気味に終わるのと同じ現象）。ユーザー
からのフィードバック：

> ページ変更しなくて良いんです。下にある余白が気持ちが悪いので。
> これ元Dataを縦長の16:9にしたらいいんじゃないかな？そういうもんじゃない？

紙に印刷する前提が無い（画面で読む・PDFとして配布するだけの）資料であれば、**そもそも
複数ページに分割せず、コンテンツの実測高さぴったりの縦長1枚に収める**のが最も
きれいに解決する。SNSの縦長インフォグラフィックと同じ考え方。ページ数が1〜2枚程度に
収まる資料では、**パターンBよりこちらをデフォルトにしてよい**。

実装手順（Chromeヘッドレスは `@page` の高さをコンテンツに自動フィットしてくれない
ため、実測→再生成の2段階が必要）：

1. **オーバーサイズな仮の`@page`高さ**（例: `720px 8000px`）でPDFを1枚生成する。
   本文がどれだけ長くても収まるよう、余裕を持たせた大きな値にする。
2. `pypdfium2` でそのページを高解像度画像化する（`scale=2.0`程度）。
3. **実コンテンツの最終行を検出する**。ここが最大の落とし穴：
   「白色(`#FFFFFF`)と異なるか」だけで判定すると**失敗する**。CSS Paged Mediaの
   仕様上、`body`の背景色（canvas色）はコンテンツの有無に関わらず**そのページ全体**
   に塗られるため、canvas色は「余白」の判定材料にならない。
   正しくは「**白でもcanvas色でもない**ピクセル（文字のインク色・カードの境界線・
   影・差し色など）が存在する最終行」を検出する：
   ```python
   from PIL import Image
   import numpy as np
   arr = np.array(Image.open('measure.png').convert('RGB')).astype(int)
   white  = np.array([255,255,255])
   canvas = np.array([0xF1,0xF0,0xEC])  # --mono-canvas の値に合わせる
   d_white  = np.abs(arr - white).sum(axis=2)
   d_canvas = np.abs(arr - canvas).sum(axis=2)
   is_content = (d_white > 20) & (d_canvas > 20)
   last_row = np.where(is_content.any(axis=1))[0].max()
   ```
4. 検出した`last_row`（画像px）を実寸に変換する：
   `content_bottom_css_px = last_row / render_scale / 0.75`
   （PDFは1pt = 1/72inch、CSS pxは1/96inch換算なので `1pt = 0.75css_px`）。
5. **最終`@page`高さ = content_bottom_css_px + 予備80px程度**を計算し、HTMLの
   `@page`定義をこの値に差し替えて再生成する（`@page margin`は`0`のまま。下側の
   余白は`.doc`の`padding-bottom`が既に担っているので、ここでの「予備」は下マージン
   分ではなく安全マージンとして加える）。
   **予備は10〜15px程度では不足することが多い。80px前後を初期値にする。**
   理由：`.card` / `.callout-strong` 等の `break-inside: avoid` は「その要素が
   ページの残り高さに収まらない場合、要素全体を丸ごと次ページへ送る」という
   all-or-nothing の挙動をする。ページ末尾ギリギリの高さで区切ると、最後の小さな
   要素（`.doc-footnote`等）だけが丸ごと2ページ目に押し出され、「あと数十pxで
   1ページに収まるはずが2ページになる」という失敗が起きやすい。
6. 生成されたPDFの**ページ数を必ず確認する**（2ページ以上になっていたら5の予備を
   さらに広げて再生成）。1ページになったら、下端の余白が上・左右の余白と同程度に
   収まっているか、左右の余白が対称か（左右で同じ`.card`行のleft/right marginを
   ピクセル計測して比較するとよい）を画像化して目視確認する。
7. 単一ページ化した場合、`.part-divider`などページまたぎを前提にしたスタイルは
   全く問題なく機能する（ページの概念自体が1枚しかないため）。

- 何ページにもなる長大な資料（10ページ超など）では、1枚に収めると縦に極端に長い
  PDFになり閲覧しづらいので、パターンB（複数ページ・自然改ページ）のままでよい。
  「1〜2ページで収まりそうな資料」を単一ページ化の目安にする。

### 5. ページ構成の優先順位

- 宿題・補足資料・参考リンクなど「知っておいてほしいが本編ではない」情報は、
  **デッキの一番最後**に置く。冒頭や中盤に挟むと本編の勢いを削ぐ。
- 表や仕組みの説明で「①②③…」と番号立てできる内容は、その番号を `badge-num`
  として視覚化すると探しやすくなる。
- ある概念の「もっと詳しく知りたくなる」補足が必要な場合は、独立した1ページを
  本編の直後に挿入し、本編側のカードから `→ 次ページで詳しく解説` のように
  リンクさせるとデッキ全体の流れが途切れない（本Skillの由来になった手法）。

## コンポーネント一覧

`template-landscape.html` / `template-portrait.html` に、以下すべての実装例が
入っている。新しいスライドを作るときは、該当ブロックをコピーして中身を差し替える。
`template-portrait-doc.html`（ドキュメント流し込み型）はこれらのコンポーネントの
うち `.card` / `.callout-strong` / `.cat-row` 等の**カード系だけ**を流用し、
`.slide` / `.content` / `grid2〜4` のようなページ単位のレイアウト要素は使わない
（本文がそのまま連続して流れるため）。

| 用途 | クラス（横長） | クラス（縦長） |
|---|---|---|
| ページ全体 | `.slide` | `.slide` |
| 見出し帯 | `.eyebrow` + `.title` + `.subtitle` + `.rule` | 同じ |
| 残り高さを埋める領域 | `.content` (+ `.center` / `.stack`) | 同じ |
| カード | `.card`（+ `.card-center` / `.card-highlight`） | 同じ |
| カードグリッド | `.grid2` / `.grid3` / `.grid4` | `.grid1`（縦積み）/ `.grid2` |
| 番号バッジ | `.badge-num` | 同じ |
| 箇条書き | `ul.plain`（`li.sub` で二階層目） | 同じ |
| セクション区切りページ | `.divider-wrap` + `.divider-num` | 同じ（数字は小さめ） |
| 時系列 | `.timeline` / `.tl-item` / `.tl-dot` | `.timeline-v` / `.tlv-item` / `.tlv-dot`（縦並び） |
| 現状→対応の対比 | `.ba-wrap` / `.ba-box` / `.ba-arrow`（→） | `.ba-stack` / `.ba-box` / `.ba-arrow-v`（↓） |
| プロセスフロー | `.flow` / `.flow-box` / `.flow-arrow`（→） | `.flow-v` / `.flow-box` / `.flow-arrow-v`（↓） |
| 核心メッセージの強調ボックス | `.callout-strong` | 同じ |
| A→Bのマッピング図 | `.mapping-row` / `.bracket-tag` / `.map-arrow` / `.color-badge` | 同じ |
| Key-Valueの説明行 | `.kv-row` / `.kv-label` / `.kv-val` | 同じ |
| フッター（ページ番号） | `.footer` | 同じ |

縦長で `grid3`/`grid4` に相当する内容（3〜4カードの横並び）が出てきた場合は、
無理に詰め込まず `.grid1`（1カラム縦積み）か `.grid2`（2カラム）で構成し直す。
横長のまま流用すると文字が窮屈になりやすい。

## アイコン素材の調達（絵文字を使わない）

`case-icon` やバッジ、tint-boxの先頭記号などに絵文字（📄✅💡など）をそのまま
使うと、デフォルトの色（黄色い月、緑のチェック等）がmono配色の「差し色1色」
ルールと衝突し、資料全体が安っぽく見える。**絵文字は使わず、必ず外部アイコン
素材に置き換える。** ユーザーから「絵文字はダサさが出る」と明示的な指摘を受けて
確立した方針。

### 1. サービス／ブランドのロゴアイコン → LobeHub Icons

Claude・ChatGPT・Gemini・Notionなど**実在サービスのロゴ**は
[LobeHub Icons](https://lobehub.com/ja/icons)（例：https://lobehub.com/ja/icons/claude ）
からSVGをダウンロードして使う。各サービスのブランドカラー付きアイコン（`claude-color.svg`
等）と、単色のシンプル版がある。ユーザーが該当サービスのアイコンをDownloadsに
保存してくれることが多いので、まずそちらを探す（`find Downloads -iname "*サービス名*"`）。
既存のダウンロード画像がロゴの一部を切り抜いた不正確なもの（スクリーンショット等）
だった場合は、LobeHubの正式なSVGに差し替えるようユーザーに提案してよい。

- ロゴがワードマーク込み（文字入り）か、アイコンのみかを確認する。アイコンのみの
  場合は、UI側で必ずサービス名のテキストラベルを添える（アイコンだけでは何の
  サービスか伝わらない）。
- 画像の実寸アスペクト比を確認してから使う（`PIL.Image.open(...).size`）。正方形で
  ない画像に `width:Npx; height:Npx` を両方指定すると引き伸ばされて歪む。正方形で
  ない場合は `object-fit: contain` を使うか、`width` のみ指定して `height: auto` にする。

### 2. 汎用アイコン（フォルダ・チェック・虫眼鏡など）→ Iconify API（lucideセット）

サービスに紐付かない汎用アイコン（before/after・チェック・検索・カレンダー等）は
[Iconify](https://iconify.design/) の公開APIから `lucide` アイコンセットを取得する。
ネットワーク接続があれば以下のコマンドで直接SVGファイルをダウンロードできる
（アカウント登録・APIキー不要）：

```bash
curl -s "https://api.iconify.design/lucide:{アイコン名}.svg?color=%23{HEXカラー（#なし）}" \
  -o "shots/icons/{アイコン名}-{用途}.svg"
```

- 色は取得時にクエリパラメータで焼き込む（`color=%2317160F` のように `#` を `%23`
  に変換する）。`currentColor` のまま埋め込んで後からCSSで制御しようとすると、
  `<img>` タグ経由の読み込みでは色が継承されず失敗するので、**取得時点で最終的に
  使う色（`--mono-ink` か `--mono-accent` の16進値）を指定してダウンロードする**。
  同じアイコンを両方の色で使いたい場合は2回ダウンロードして
  `{name}-ink.svg` / `{name}-accent.svg` のように保存し分ける。
- アイコン名は [lucide.dev](https://lucide.dev/icons/) で検索して確認する（例：
  `folder-open`, `circle-check-big`, `handshake`, `search`, `moon`, `map-pin`,
  `calendar`, `users`, `building-2`, `landmark`, `smile`）。
- ダウンロード後、`wc -c` でファイルサイズが100バイト未満でないか（＝404エラー
  ページを保存していないか）を必ず確認する。

### 3. アイコンの使い方の原則

- `case-icon` の中身は絵文字テキストではなく `<img class="ico" src="shots/icons/xxx.svg"
  style="width:Npx;height:Npx;">` にする。サイズは元の絵文字フォントサイズと同じ
  px値をそのまま流用すれば大きさの調整は不要なことが多い。
- 差し色（`--mono-accent`）を使ってよいのは、`case-highlight` の中のアイコンや、
  警告・強調のためのアイコン（`triangle-alert` 等）だけ。それ以外は `--mono-ink`
  （黒系）で統一し、色のバラつきで資料が騒がしくならないようにする。
- ネットワーク接続が使えない環境では、Iconify取得の代わりにLobeHub/ユーザー提供
  画像で代替するか、取得済みの `shots/icons/` 配下を使い回す。

## カラー定義（color-monoを継承）

```css
:root {
  --mono-canvas: #F1F0EC;
  --mono-card:   #FFFFFF;
  --mono-ink:    #17160F;
  --mono-sub:    #66655D;
  --mono-faint:  #9B9A90;
  --mono-line:   #E8E7E1;
  --mono-accent: #FF3B1F;      /* 1資料1色。バッジ・強調枠・矢印のみ */
  --mono-accent-tint: #FFEFEA;
}
```

案件のブランドカラーが別途指定された場合は `--mono-accent` / `--mono-accent-tint`
だけを差し替える（`color-mono` 参照）。グレー階調はそのまま流用してよい。

## PDF化コマンド（Windows / Chrome）

HTMLファイルをスライド風に組んだら、Chromeヘッドレスで直接PDF化する。
wkhtmltopdf・weasyprint等は使わない（日本語フォント・CSS Grid対応が弱いため）。

```bash
"/c/Program Files/Google/Chrome/Application/chrome.exe" --headless --disable-gpu \
  --no-pdf-header-footer --print-to-pdf="出力先.pdf" --print-to-pdf-no-header \
  --run-all-compositor-stages-before-draw --virtual-time-budget=10000 \
  "file:///絶対パス/スライド.html"
```

- `@page { size: 1280px 720px; margin: 0; }`（横長）/ `size: 720px 1280px;`（縦長）を
  HTML側のCSSに必ず入れておくこと。これがそのままPDFのページサイズになる。
- 出力先パスに日本語ユーザー名等が含まれると `ERROR ... アクセスが拒否されました`
  で失敗することがある。その場合は `C:\temp\` のような単純なパスに一旦出力し、
  最後に目的のファイル名へコピーする。

## PDF検証コマンド（必須）

生成したPDFは必ず画像化して目視確認する。文字のはみ出し・余白の偏りはテキスト
情報だけでは分からない。

```bash
C:/Python314/python.exe -c "
import pypdfium2 as pdfium
pdf = pdfium.PdfDocument('出力先.pdf')
print('pages:', len(pdf))
for i in range(len(pdf)):
    page = pdf[i]
    bitmap = page.render(scale=1.3)
    bitmap.to_pil().save(f'check_p{i+1:02d}.png')
"
```

保存した `check_pXX.png` を `Read` ツールで開いて確認する。特に：
- カード内の文章がカードの下端・スライド下端をはみ出していないか
- 情報量が薄いページで不自然に上寄せ/中央寄せになっていないか
- ヘッダーとフッターが重なっていないか（`.footer` は `position:absolute` なので
  コンテンツが伸びすぎると重なる）
